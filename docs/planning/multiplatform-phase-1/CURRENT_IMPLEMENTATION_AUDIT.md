# Current Implementation Audit

**Scope:** source inspection of the current `main` checkout. Production source was not changed. Line references point to the source state reviewed on 2026-10-29.

## Findings that change the starting assumptions

### The scanner still uses Vision

The current source does not implement time-only grouping. `SimilarityScanner` imports Vision, first builds capture-time clusters, requests image representations for multi-item clusters, generates `VNFeaturePrintObservation`s, and then splits/refines image connected components by a feature-print distance threshold. This path is used for both Photos and Folder items. See [SimilarityScanner.swift:1-4](../../../Sources/PhotoSortHelper/SimilarityScanner.swift#L1), [169-237](../../../Sources/PhotoSortHelper/SimilarityScanner.swift#L169), [333-385](../../../Sources/PhotoSortHelper/SimilarityScanner.swift#L333), and [387-531](../../../Sources/PhotoSortHelper/SimilarityScanner.swift#L387).

The assignment explicitly requires no Vision. That requirement conflicts with the executable path in source, so Phase 2 must replace the feature-print refinement while preserving the specified adjacent-gap grouping and video-singleton behavior. This audit does not change production behavior.

### Destination albums do not currently mean “already sorted”

Photos scans fetch image assets, optionally videos, and optional date constraints; they do not exclude assets in `Fully Sorted`, `Files to Manually Delete`, or `Files to Edit`. The app currently uses these albums only as destinations when the user commits a review. There is no Continue Sorting / unsorted-library workflow. See [PhotoLibraryService.swift:142-200](../../../Sources/PhotoSortHelper/PhotoLibraryService.swift#L142) and [748-776](../../../Sources/PhotoSortHelper/PhotoLibraryService.swift#L748), plus [ReviewViewModel.swift:1388-1467](../../../Sources/PhotoSortHelper/ReviewViewModel.swift#L1388).

### Group completion and skip behavior differ from the new workflow

The existing review view marks a group reviewed as soon as it appears, not when the user advances. `Next Group` only changes the index; no Skip Group action exists. See [ReviewViewModel.swift:745-757](../../../Sources/PhotoSortHelper/ReviewViewModel.swift#L745) and [RootView.swift:1036-1047](../../../Sources/PhotoSortHelper/RootView.swift#L1036). The new explicit “Next Group finishes; Skip leaves unresolved” behavior is a real workflow change.

## Scan and grouping behavior in the current source

1. Photos mode fetches the whole selected Photos scope into an array. A scope can be All Photos or one album/collection list, with date bounds and an optional video filter. Fetch options request image assets and, when enabled, video assets, then ask PhotoKit to sort by `creationDate` ascending. See [PhotoLibraryService.swift:142-200](../../../Sources/PhotoSortHelper/PhotoLibraryService.swift#L142) and [748-775](../../../Sources/PhotoSortHelper/PhotoLibraryService.swift#L748).
2. Each Photos item uses `creationDate ?? modificationDate` as its preferred date. Missing both dates sort as `.distantPast`. The item ID is the device-local `PHAsset.localIdentifier`. See [PhotoLibraryService.swift:207-223](../../../Sources/PhotoSortHelper/PhotoLibraryService.swift#L207) and [Models.swift:163-205](../../../Sources/PhotoSortHelper/Models.swift#L163).
3. The scanner independently sorts by preferred date, then ID, and creates **transitive adjacent-gap clusters**: each next item joins while its gap from the immediately preceding item is at most the setting. The current default is 8 seconds, configurable from 2 to 30 seconds in Settings. A sequence of 7-second gaps can therefore make a group span much longer than 8 seconds. See [SimilarityScanner.swift:299-331](../../../Sources/PhotoSortHelper/SimilarityScanner.swift#L299), [ReviewViewModel.swift:59-63](../../../Sources/PhotoSortHelper/ReviewViewModel.swift#L59), and [PreferencesView.swift:37-39](../../../Sources/PhotoSortHelper/PreferencesView.swift#L37).
4. A time cluster containing one item becomes a one-item review group directly. For larger clusters, videos are emitted individually; images are subject to the Vision refinement described above. A photo without a usable feature print has no matching edge and ends up in its own component. See [SimilarityScanner.swift:210-238](../../../Sources/PhotoSortHelper/SimilarityScanner.swift#L210) and [387-505](../../../Sources/PhotoSortHelper/SimilarityScanner.swift#L387).
5. Live Photos are `PHAsset.mediaType == .image`, receive a `LIVE` badge from their media subtype, and participate in photo grouping. The app requests ordinary image thumbnails and has no `requestLivePhoto`/motion playback path. Videos are excluded by default in the existing preferences; when enabled, they remain singleton groups even when their dates are near other items. See [PhotoLibraryService.swift:207-221](../../../Sources/PhotoSortHelper/PhotoLibraryService.swift#L207), [787-810](../../../Sources/PhotoSortHelper/PhotoLibraryService.swift#L787), and [SimilarityScanner.swift:394-414](../../../Sources/PhotoSortHelper/SimilarityScanner.swift#L394).
6. Items in an image group are ultimately normalized by sorting their IDs lexicographically, not by capture time. This comes after the scanner initially orders component items by date. Group order is by group start date (missing date first), with IDs as a tie-breaker. See [ScanBatching.swift:114-141](../../../Sources/PhotoSortHelper/ScanBatching.swift#L114).

The scanner therefore has two separate ordering concepts today: groups are chronological; items within each normalized group are ID-sorted. Treat that ID ordering as the observed existing behavior for parity and add a test; change it only through an explicit product decision.

## Review modes, explicit decisions, Edit, and commits

- `Discard-first` displays unmarked items as discard; a user can explicitly keep or queue an item for editing. `Keep-first` displays unmarked items as “review-only keep”; only explicit keeps are queued for `Fully Sorted`. The distinction is represented by `ReviewGroupDecisions.explicitKeepIDs` / `explicitDiscardIDs` plus a separate app-wide `queuedForEditItemIDs` set. See [Models.swift:20-43](../../../Sources/PhotoSortHelper/Models.swift#L20), [208-216](../../../Sources/PhotoSortHelper/Models.swift#L208), and [ReviewViewModel.swift:1704-1753](../../../Sources/PhotoSortHelper/ReviewViewModel.swift#L1704).
- `Edit` is a local override that is stored in `queuedForEditItemIDs`; the selected item is also treated as an explicit keep for review display, but the Edit destination takes precedence in the commit plan. See [ReviewViewModel.swift:952-979](../../../Sources/PhotoSortHelper/ReviewViewModel.swift#L952) and [1388-1458](../../../Sources/PhotoSortHelper/ReviewViewModel.swift#L1388).
- The Mac UI has separate group navigation and classification controls, but “reviewed” is currently tied to having displayed a group. The new workflow requires an explicit completion boundary and a distinct Skip action.
- Decisions stay in the local session until the user opens the summary and explicitly commits. Photos outcomes are additions to the three review albums; the app does not delete Photos assets. The three names are defined in [ReviewViewModel.swift:139-141](../../../Sources/PhotoSortHelper/ReviewViewModel.swift#L139).
- The existing Photos commit performs up to three independent `queueAssets` calls, one for each destination. Each call re-fetches the assets, checks membership in that one target album, creates the album if no case-insensitive title match exists, and adds the missing assets. The app updates local session state after the calls complete. There is no cross-destination preflight, cross-device conflict detection, or single transaction for all outcomes. See [ReviewViewModel.swift:1404-1463](../../../Sources/PhotoSortHelper/ReviewViewModel.swift#L1404) and [PhotoLibraryService.swift:539-597](../../../Sources/PhotoSortHelper/PhotoLibraryService.swift#L539).
- Album lookup returns the first case-insensitive name match. Duplicate names are not detected; this conflicts with the new no-guess requirement. See [PhotoLibraryService.swift:920-929](../../../Sources/PhotoSortHelper/PhotoLibraryService.swift#L920).

Changing review mode during an active Mac session requires confirmation and then clears the current session; it does not retain completed group decisions. See [ReviewViewModel.swift:426-447](../../../Sources/PhotoSortHelper/ReviewViewModel.swift#L426), [1685-1693](../../../Sources/PhotoSortHelper/ReviewViewModel.swift#L1685), and [PreferencesView.swift:84-93](../../../Sources/PhotoSortHelper/PreferencesView.swift#L84). The new cross-scope queue must freeze each staged classification so a later mode change cannot reinterpret it.

## Persistence and recovery

The Mac app stores the current review session as `review-session-v2.json`, scan preferences as `scan-preferences-v2.json`, and optional batch continuation as `scan-batch-state-v1.json` under Application Support. Session state includes the scanned items/groups, active group and photo, review mode, group-level explicit decisions, edited IDs, reviewed group IDs, scope settings, and current position. See [AppPaths.swift:3-60](../../../Sources/PhotoSortHelper/AppPaths.swift#L3) and [StoredReviewSession.swift:3-29](../../../Sources/PhotoSortHelper/StoredReviewSession.swift#L3).

The session and preference writers use JSON with ISO-8601 dates and atomic file replacement. Session saves are debounced by 300 ms; restore re-fetches Photos assets by their saved local identifiers, filters items that cannot be fetched, and anchors to group/photo IDs when possible. The decoder accepts legacy field names and the startup migration searches older filenames and bundle-ID locations. See [ReviewViewModel.swift:1862-1884](../../../Sources/PhotoSortHelper/ReviewViewModel.swift#L1862), [1885-1958](../../../Sources/PhotoSortHelper/ReviewViewModel.swift#L1885), [1977-2029](../../../Sources/PhotoSortHelper/ReviewViewModel.swift#L1977), and [2074-2097](../../../Sources/PhotoSortHelper/ReviewViewModel.swift#L2074). Preference migration also reads older JSON and UserDefaults locations; see [ScanPreferencesStore.swift:117-203](../../../Sources/PhotoSortHelper/ScanPreferencesStore.swift#L117).

The current model is one active scan/session, not multiple resumable scope sessions backed by one shared per-photo queue. A Photos local identifier is the only Photos asset key in stored sessions. There is no per-commit intent journal. The iOS app must use its own local app container; it should not copy macOS folder bookmarks or treat device-local pending work as synced.

## PhotoKit access and media preparation

`PhotoLibraryService` checks/request read-write authorization, and the view model requests access only when scanning or queueing. The existing Mac handles `.authorized` and `.limited` as possible states and explains their limitations. See [PhotoLibraryService.swift:101-111](../../../Sources/PhotoSortHelper/PhotoLibraryService.swift#L101) and [PhotoAuthorizationSupport.swift:3-56](../../../Sources/PhotoSortHelper/PhotoAuthorizationSupport.swift#L3).

The service uses `PHCachingImageManager`; thumbnails and video requests allow network access. Vision grouping can request 320-pixel images for every photo in a multi-item time cluster before review. Review prefetch separately asks for thumbnails for up to 12 items in the next group and a larger preview for the selected photo. iCloud download progress is not surfaced by the current request handlers. See [PhotoLibraryService.swift:284-359](../../../Sources/PhotoSortHelper/PhotoLibraryService.swift#L284), [383-490](../../../Sources/PhotoSortHelper/PhotoLibraryService.swift#L383), and [ReviewViewModel.swift:1841-1860](../../../Sources/PhotoSortHelper/ReviewViewModel.swift#L1841).

Video preview is requested as an `AVPlayerItem` and displayed through an AppKit view. No manual two-photo compare view or Live Photo motion view exists. `PHPhotoLibraryChangeObserver` is not registered, so external changes are not incrementally reflected in the active session.

## Mac-only behavior and current architecture

`Package.swift` defines one SwiftPM **macOS 26 executable target**, with an embedded Info.plist linker flag and one test target. There is no Xcode project, iOS app target, shared core library, or iOS simulator scheme. The executable app has a SwiftUI `@main`, a main window, standard Settings, and a dedicated About window. See [Package.swift](../../../Package.swift), [PhotoSortHelperApp.swift:3-20](../../../Sources/PhotoSortHelper/PhotoSortHelperApp.swift#L3), and [MainWindowScene.swift:3-16](../../../Sources/PhotoSortHelper/MainWindowScene.swift#L3).

Photo metadata/group/decision types are internal app-target types. The same source set mixes Foundation domain concepts with Photos, Vision, AppKit, AVKit, and folder/file concerns. `ReviewViewModel.swift` (2,239 lines) centralizes scope, authorization, scanning, decisions, restoration, Photos/Finder operations, preview caching, and commits; `RootView.swift` is also a large view file. The scanner is named `SimilarityScanner`, and its design is coupled to Vision.

Folder mode is a first-class Mac capability: the user chooses a directory through `NSOpenPanel`; a security-scoped bookmark is retained; recursive traversal skips hidden items, package directories, and symlinked entries; ImageIO/AVFoundation metadata provide dates; and writes are previewed and moved only into supported destination folders after the explicit commit step. See [FolderLibraryService.swift:17-104](../../../Sources/PhotoSortHelper/FolderLibraryService.swift#L17) and [154-220](../../../Sources/PhotoSortHelper/FolderLibraryService.swift#L154), and [FolderCommitService.swift:20-113](../../../Sources/PhotoSortHelper/FolderCommitService.swift#L20).

Finder actions, `NSWorkspace`, `NSEvent`, `NSViewRepresentable`, `NSOpenPanel`, and AppKit video playback belong to the Mac shell. The native multi-scene design, menus, and Mac keyboard handling should remain there rather than be forced into iOS. See [ReviewViewModel.swift:517-606](../../../Sources/PhotoSortHelper/ReviewViewModel.swift#L517), [RootView.swift:242-340](../../../Sources/PhotoSortHelper/RootView.swift#L242), and [ReviewKeyboardAction.swift](../../../Sources/PhotoSortHelper/ReviewKeyboardAction.swift).

## Tests and uncovered behavior

The current 15 XCTest methods cover release version helpers, preference migration, legacy session decoding, folder traversal/commit planning, Photos permission wording, local Edit staging, queue planning, source-reset behavior, keyboard mapping, and batch-checkpoint validation/continuation. One scanner test verifies frozen video continuation across batches. See [AlignmentTests.swift](../../../Tests/PhotosLibrarySortHelperTests/AlignmentTests.swift), [ReviewKeyboardActionTests.swift](../../../Tests/PhotosLibrarySortHelperTests/ReviewKeyboardActionTests.swift), and [ScanBatchingTests.swift](../../../Tests/PhotosLibrarySortHelperTests/ScanBatchingTests.swift).

Important gaps include focused tests for adjacent-gap boundaries, long transitive chains, nil-date order, equal-date tie breaking, the post-normalization order of items inside groups, missing Vision images, Live Photo playback, destination-album duplicate/rename/membership cases, partial PhotoKit commit failure, local crash reconciliation, iCloud permission/download progress, multi-scope queue migration, limited iOS access, and two-device conflicts. The existing XCTest suite does not substitute for PhotoKit integration testing on devices with a real test library.
